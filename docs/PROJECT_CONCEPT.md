# GPU Explorer：项目构想

> 一颗能拆开、运行、解释、比较的“透明 GPU”。

**状态：概念提案 / 尚未开始实现**  
**首次记录：2026-11-01（Asia/Singapore）**  
**用途：保存本轮讨论形成的产品方向，为后续设计和开发提供起点。**

本文区分长期愿景、第一版建议和后续探索。用户认可并保存了这个方向，具体架构、功能取舍、实现排期、技术栈和许可证仍需后续决定。

## 1. 核心定位

做一部可以操作的 GPU 教科书。用户能理解 GPU 的组成，也能让它完成一个具体任务，观察工作、数据和硬件资源如何联系起来。

产品应同时具有：

- **探索硬件的乐趣**：拆开、进入、选中、隔离、比较。
- **解释过程的能力**：从输入到结果，随时停下来问“这里发生了什么”。
- **知识的连续性**：结构、代码、状态和设计原因互相连接。
- **由浅入深的内容**：初学者先理解用途，熟悉 GPU 的用户继续展开线程、内存、指令和资源限制。
- **可持续扩展的内容体系**：便于增加架构、实验和课程。

GPU 图形与通用计算都属于长期范围。Kernel 优化作为进阶内容，不能让整个产品在入口处就收缩成只服务于 CUDA 优化人员的工具。

一句话的产品承诺：

**从“这是什么”，一路点到“它为什么这样工作”，再亲手改变条件查看结果。**

## 2. 现有项目：实测评价与机会

以下评价来自本轮实际浏览器操作，是产品体验判断。范围主要为 GPU 相关路径，不代表对整个网站所有页面的审计。

### 2.1 PC Anatomy

- 网站：https://pc-anatomy.com/
- SM 入口：https://pc-anatomy.com/?scale=sm
- 仓库：https://github.com/Yoosseph/pc-anatomy

**结论：三者中成品感和结构探索完成度最好。模型做得比知识讲得深。**

实际测试包括：

- 在 GPC 模型中点进 TPC，再进入 SM，层级与面包屑同步变化。
- 旋转、缩放和俯视视角。
- 选中具体 warp scheduler，查看部件卡片。
- Focus、Isolate、Show context 等操作。
- 悬停识别单个 CUDA core。
- Assembled、50% Dissection、100% Inventory。

值得借鉴的是连续层级、组件拾取、聚焦与隔离，操作围绕同一套结构组织。其短板是部件解释通常简短，用户容易知道名称与用途，却仍不知道部件如何协作完成任务。

本次体验中的具体摩擦：

- SM 在 100% Inventory 下被拆成许多小部件，分组关系反而不如 50% Dissection 清楚。
- 底部 Reset camera and assembly 将探索返回 Desktop PC 根层级，超出按钮名称暗示的范围。

其页面明确说明内部几何属于逻辑架构示意，不能当成真实晶体管布局。

### 2.2 GEX — GPU Execution Explorer

- 网站：https://gex.aserdargun.com/gex/anatomy?lang=en
- Warp 示例：https://gex.aserdargun.com/gex/warp?lang=en
- Memory 示例：https://gex.aserdargun.com/gex/memory?lang=en

**结论：有教学内容的原型，基础状态联动有效，但解释深度和 3D 的教学收益仍有限。**

实际测试中：

- Anatomy 与 SM 场景正常渲染，模型、颜色与标签统一。
- Divergent / Path A 下偶数 lane 亮起；选中 lane 1 显示 Masked。
- 切换 Path B 后，同一个 lane 1 显示 Active。
- 更改访存模式时，地址关系、代码和地址组统计一起改变。
- 步骤、分支模式和选中 lane 可以保留在分享链接中。
- 文字模式还检查了 kernel 工作划分、SM 调度示例和 tiled GEMM 参数联动；这些不等同于逐一审计所有 3D 场景。

它说明了“交互教学”已经有人做出可用内容。新项目需要在知识深度和探索组织上继续推进。

不足：

- Warp 等场景主要依赖格子颜色、选中状态与时间轴传递信息；单纯把格子做成立体块，新增理解价值有限。
- 在本次约 1920 × 900 的视口里，大场景将时间轴和代码推到下方，用户需要来回滚动才能对照。
- 教学状态与例子相对局部，还没有形成一颗完整 GPU 的连续探索体验。

其教学地址组不是 profiler 事务数，动画步骤也不是实测硬件时间。模型边界的说明值得借鉴。

### 2.3 Accelerator Visualizer

- 网站：https://staru09.github.io/gpu_viz/
- 仓库：https://github.com/staru09/gpu_viz

**结论：三者中最粗糙，更接近展示 demo / 半成品；型号菜单明显大于实际内容深度。**

实际测试了通用 GPU、GH100、MI300X 和 CUDA 模式：

- 旋转、缩放、悬停说明和组件显隐有效。
- GH100 的 HBM 选项确实控制相应部件显示。
- 点击 GH100 中的 SM，仍停留在整颗芯片视图，没有进入更深的内部探索。
- CUDA 模式有独立二维动画，阶段切换、暂停和继续有效。

主要短板：

- 几何、材质和构图比较简单。
- 缺少持续场景标签，依赖逐个悬停读说明。
- 看完几块彩色区域和参数卡后，内容很快见底。
- CUDA 动画与具体 GPU 型号模型分离，未形成连续过程。

### 2.4 我们应该做出的区别

以 PC Anatomy 的探索能力作为起点，把部件背后的过程和解释补上。每一次进入、选择或修改，都应带来新的理解。

机会主要在：

1. 连接硬件、软件工作、数据和执行状态。
2. 从部件用途继续深入到协作关系与设计原因。
3. 让一个真实问题在多个尺度间连续展开。
4. 让比较解释设计取舍，而非只排列型号和规格。
5. 让用户能够检验自己的理解，并分享讲解过程。

## 3. 三个入口与两条核心旅程

### 3.1 三个入口

| 入口 | 核心体验 |
| --- | --- |
| **拆开看看** | 从板卡、封装进入芯片和执行资源，观察组成、连接和共享关系。 |
| **让它做点事** | 选一个教学任务，跟随工作和数据，查看代码与状态。 |
| **和另一颗比较** | 锁定正在研究的问题，对照另一代或另一家架构的实现。 |

三个入口使用同一套知识与模型。切换入口时，尽量保留选中对象、实验参数和当前问题。

### 3.2 旅程 A：一次矩阵乘法如何完成

用户先看到小矩阵 A、B 和输出 C，再选中 C[3,7]。

网站逐层展开：

1. 该结果依赖哪些输入与计算。
2. 当前示例如何划分输出 tile 和 block。
3. 哪些线程或线程组参与这一部分工作。
4. 输入当前存放在哪里，如何准备和搬运。
5. 哪些输入被复用。
6. 哪一步计算、哪一步等待或同步。
7. 改变实现以后，数据搬运、资源占用与工作分配有什么变化。

提供简单实现和进一步优化的实现，逐步展开。对矩阵专用单元的说明必须对应具体架构和具体示例，避免把所有矩阵乘法画成同一种执行方式。

用户随时可以退回全 GPU 视图，观察其他计算单元的工作分布。

### 3.3 旅程 B：一个像素如何画出来

用户从一个像素或简单场景进入，查看与它有关的几何、采样和处理阶段，以及相关硬件的职责。

目的：

- 为计算主线以外的用户提供直观入口。
- 解释 GPU 图形用途和专用硬件为什么存在。
- 连接用户认识的结果与内部处理过程。

具体图形 API、渲染路径和硬件型号留待设计，不在当前文档中假定所有 GPU 都具有相同流水线。

## 4. 内容完整度标准

### 4.1 六块内容

| 内容 | 覆盖对象 | 应能回答的问题 |
| --- | --- | --- |
| **物理结构** | 板卡、封装、计算芯片、显存、堆叠和连接 | 我看到的 GPU 产品由哪些东西组成？ |
| **内部架构** | 计算集群、SM / CU、执行单元、寄存器、缓存、共享存储 | 各部件负责什么，为什么这样分组？ |
| **工作分配** | grid、block、warp、线程与硬件资源的映射 | 大量线程怎样使用有限的硬件？ |
| **执行过程** | 发射、依赖、等待、同步、重叠 | 哪些工作在推进，哪些在等待，为什么？ |
| **数据与内存** | 地址、访问模式、缓存、显式复用、共享范围 | 数据在哪里，怎样获取和复用？ |
| **实际任务** | 向量运算、矩阵乘法、图形；后续 attention 和多 GPU | 这些部件最终怎样完成一个具体任务？ |

### 4.2 每个重要部件的最低内容

每个重要部件都应有：

- 职责。
- 输入与输出。
- 上下游及协作关系。
- 共享范围。
- 资源限制或等待条件。
- 一个可操作的例子。
- 资料来源与适用架构。

“画出一个方块，再附一行定义”不算完整内容。

### 4.3 shared memory 的内容样例

这一项至少应允许用户查看：

- **位置**：当前架构中的资源区域。
- **范围**：当前例子里谁能访问同一份数据。
- **准备**：示例怎样把数据准备好。
- **协作**：写入、同步与读取如何配合。
- **复用**：同一份输入被哪些计算重复使用。
- **代价**：分配更多空间后，其他工作还有多少可用资源。
- **反例**：一个不正确的同步方式或不合适的访问模式。

内容必须区分物理资源与程序可见的使用范围，例如 SM 的资源与 block 的分配、访问规则；不能仅靠几何位置暗示所有线程都能任意共享。

## 5. 硬件覆盖策略

优先把少量有代表性的架构做深，再扩展能体现不同设计选择的硬件。

### 5.1 建议的第一批代表

| 代表 | 作用 | 建议深度 |
| --- | --- | --- |
| **H100** | 计算主线的主角 | 结构、工作分配、访存、矩阵计算；进阶到异步搬运与协作。 |
| **一款消费级 RTX** | 图形主线 | 配合“一个像素”的旅程解释图形处理和专用资源。 |
| **AMD MI300X** | 不同封装与架构设计的比较 | 多芯粒、堆叠、计算与 I/O 分工，同一问题在另一种组织中的实现。 |

Hopper 的 TMA、thread block cluster 与 distributed shared memory，以及 CDNA 3 的计算芯粒 / I/O die 组织，可以形成各自有明确主题的专题。[1][2]

上述选择是建议，具体 SKU 尚未决定。数据组织应区分架构、完整芯片设计和实际产品配置，避免将完整芯片资源直接当成每款产品的启用资源。

### 5.2 代际演化

以 A100 → H100 等有明确变化的架构对为例：

- 保留已理解的基础结构。
- 高亮新增、移除或调整的部分。
- 解释变化对应什么问题。
- 用一个任务对照如何利用新能力。

时间轴的重点是设计演化和工作方式，规格表作为辅助。

### 5.3 跨厂商比较

比较围绕相同问题展开：

- 工作怎样分组？
- 怎样共享或搬运数据？
- 矩阵计算交给什么资源？
- 内存与计算怎样组织？

用户切换架构时，保留正在研究的概念，显示各自实现。不要把 SM、CU 等强行视作一一等价，也不要用同一套方块换个标签假装完成了架构覆盖。

Intel、Apple、TPU 等为后续探索方向。每新增一种，应带来有内容的设计比较；资料不足之处保持明确。

## 6. 交互设计

### 6.1 连续进入并保留上下文

不同尺度可以使用不同表达：

| 尺度 / 关系 | 优先表达 |
| --- | --- |
| 封装、堆叠、空间连接 | 3D、拆解、剖切 |
| 逻辑架构与资源分组 | 清晰的架构图，可带立体层级 |
| 线程、地址与矩阵 | 2D 网格与对应高亮 |
| 依赖、等待与重叠 | 事件和时间轴 |

保留面包屑、选中对象和小型全局视图。进入 SM 的执行现场时，要明确从硬件结构切换到了软件工作与状态。

### 6.2 从结果倒查，或跟随输入前进

- 点击 C[3,7]，展开相关输入、工作和数据路径。
- 点击一个像素，查看参与生成它的处理过程。
- 点击一份输入，查看当前示例中哪些计算使用它。

为大规模任务提供聚合视图，选中后再展开局部，避免把所有线程和数据都同时画出来。

### 6.3 五种观察视图

| 视图 | 强调的信息 |
| --- | --- |
| **结构** | 部件、归属和连接 |
| **工作分配** | block、warp 等工作如何映射到资源 |
| **数据** | 存放、读取、搬运与复用 |
| **等待** | 当前等待的工作及原因 |
| **资源占用** | 寄存器、shared memory 等资源分配 |

同一个被选中对象在各视图中对应高亮，切换视图时不丢失实验状态。

### 6.4 改变条件并对照前后

建议实验：

- 改变地址访问方式。
- 改变 block 大小、tile 或任务总量。
- 比较不同数据复用方式。
- 比较同步与异步组织。
- 观察资源分配与工作覆盖的变化。

保留修改前的状态、淡色轮廓或并列时间轴。解释哪些搬运减少、哪些资源增加、哪些工作划分发生变化。

教学实验先使用明确规则。实际性能比较使用可复现的测量结果；不能仅根据动画或资源条长短生成看似精确的速度数字。

### 6.5 先预测，再播放

在场景中给用户短问题：

- 哪些 lane 会执行？
- 哪些访问会聚在一起？
- 这个 block 为什么还不能放进去？
- 分更多小任务会带来什么变化？
- 哪种实现需要搬更多数据？

让用户直接点模型或选状态，再播放过程并解释答案。

### 6.6 可分享的讲解路径

讲解者可以选架构、视角、步骤和注释，分享一个链接。

接收者可跟随讲解，也可暂停、自由探索，再返回讲解进度。分享状态应能恢复架构、场景、参数、选中对象和当前步骤。

这可服务于教程、博客、技术讨论和演示，不只是单人浏览。

### 6.7 同屏对照

模型、相关代码、事件控制与当前解释应方便同时查看。常用操作不应要求用户不断上下滚动寻找。

布局允许折叠次要面板，当前代码和对象保持关联。窄屏采用明确切换的视图，保留选中状态与步骤。

## 7. 第一版建议

第一版先围绕一颗可以完整探索的 GPU 建立计算主线，H100 是当前建议。

候选场景：

| 场景 | 核心学习结果 |
| --- | --- |
| 封装到 SM 的结构探索 | 知道各尺度的组成与关系。 |
| 向量计算与工作分配 | 理解软件工作怎样使用有限硬件。 |
| Warp 分支与执行状态 | 区分线程身份、活跃状态与执行资源。 |
| 访存模式 | 理解地址模式改变了什么。 |
| 矩阵乘法 | 追踪输出依赖、数据复用和不同实现。 |
| 资源与工作量 | 区分驻留、工作覆盖、等待与尾部工作。 |

配套基础能力：

- 可选中、聚焦、隔离和返回上下文。
- 模型、代码与事件联动。
- 可重置、逐步推进和回看。
- 可恢复的分享链接。
- 清楚的来源与示例假设。

**这是一组建议范围，不是所有内容一次性实现的承诺。** 应先选一条完整旅程，验证探索、解释和修改条件能连成一个完整体验，再扩展其他场景。

### 首条旅程的验收问题

- 用户能否从整体进入具体部件，并知道自己的位置？
- 选中一个输出后，能否看清相关输入和工作？
- 当前代码与当前状态是否一致？
- 修改条件后，能否解释变化，而不是只看到动画改变？
- 返回上一层或切换视图后，上下文是否保留？
- 分享链接能否恢复同一个问题现场？

## 8. 后续方向

### 8.1 图形主线与跨架构比较

加入消费级 GPU 的像素旅程、AMD 封装与架构比较，以及代际演化时间轴。

### 8.2 更深入的工作负载

Attention、多 GPU 通信、计算与搬运重叠、实际优化前后案例。先用完整、可解释的代表例子展开，再考虑更广泛覆盖。

### 8.3 “自己设计一颗 GPU”

一个有明确规则的教学游戏：

- 给定资源预算。
- 在计算、存储和搬运能力之间分配。
- 用不同任务观察设计的表现。
- 通过调整理解架构取舍。

目标是让用户体验选择与后果。模型规则与真实硬件性能保持区分，不把游戏分数包装成芯片性能预测。

### 8.4 后续需研究的能力

- 更自由的代码编辑。
- 真实 profiler 数据与教学场景的连接。
- 讲解制作、嵌入和协作。
- 更广的硬件覆盖。

这些仍是研究方向，未承诺具体功能或实现路径。

## 9. 内容可信度与工程原则

### 9.1 三种内容保持区分

1. **有资料依据的硬件事实**：注明架构、产品配置和来源。
2. **教学模型的状态与规则**：说明当前例子怎样简化。
3. **实际测量**：附环境、输入、代码版本和测量方法。

动画时间不是实测延迟，示意地址组不是 profiler 事务数，逻辑方块位置不是晶体管布局。

### 9.2 分开表示硬件、工作与时间

- 硬件资源包括执行单元、存储与连接。
- 软件工作包括线程、block、warp 及任务划分。
- 事件表示这些工作在资源上的活动和依赖。

这种区分既服务于正确解释，也便于切换架构和视图。[3]

### 9.3 内容可维护、可贡献

统一描述：

- 架构和产品配置。
- 部件及关系。
- 概念说明与来源。
- 实验参数、事件和状态。
- 课程路径与注释。

希望贡献者能增加资料、实验和讲解，而不必理解整个 3D 渲染实现。具体数据格式和技术栈留待设计。

### 9.4 对第一版复杂度的取舍

第一版优先使用可解释的预设例子与可编辑参数。任意 CUDA 程序的完整执行可视化、精确硬件仿真和所有架构的等深度支持，属于更大的独立范围。
